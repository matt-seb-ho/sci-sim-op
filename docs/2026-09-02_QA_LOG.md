## Q1. Why did per-rollout cost blow up 5×, from $0.0381 to ~$0.194?

**Not pricing.** Verified live against OpenRouter on 2026-09-02:
`z-ai/glm-5.3-flash` is **$0.075/M in, $0.250/M out** — identical to what
`2026-08-26_BUDGET_PLAN.md` quoted.

**It is turn count, and input tokens are the entire bill.** Every turn resends
the conversation, so cost grows superlinearly in turns. Output is negligible
(~138k tokens ≈ $0.03/rollout).

| | budget plan (n=2) | 2026-09-02 (n=18) |
|---|---|---|
| turns / tool calls | 39 | **138.6** |
| input tokens / rollout | — | **9.7 M** |
| $/rollout | $0.0381 | **~$0.194** |

Split by outcome, the tail is the cost:

| outcome | n | mean turns | mean input tokens |
|---|---|---|---|
| completed | 8 | 84 | 4.5 M |
| **timed out** | **9** | **199** | **15.3 M** |

**Three causes, in order of size:**

1. **The agent ran full GEOS simulations** — see Q3. Not asked for, and the
   dominant term.
2. **The box is oversubscribed by other users.** Load average **119.98 on 128
   cores** (15-min), from `SimWorld`/`SimWorldEditor` processes owned by five
   other accounts, with zero `geosx` of ours running at the time of measurement.
   Wall-clock timeouts are substantially other people's load.
3. **Setup got heavier.** D2 vendored `required_sections`, `constraints` and
   `cross_section_refs` into the stop policy on top of `parse` and
   `geosx_validate` — each is another way the Stop hook blocks and sends the
   agent round again. Timeout was also raised 1800 s → 2400 s. Both were the
   right calls; neither was priced.

**Consequence for the grant number:** `2026-08-26_BUDGET_PLAN.md`'s "$21 for 560
rollouts" reads **≈$109 as configured on 2026-09-02**, or roughly **$40** with a
turn cap. Say which you are quoting.

## Q2. Is `glm-5.3-flash` simply worse at this task than `deepseek-v4-flash-0423`?

**Cannot be concluded from this evidence, and should not be claimed.** The
difference is real and large, but it is confounded three ways.

| | SIGA CC arm + deepseek-v4-flash (n=36) | 2026-09-02 CC+adapter + glm-5.3-flash (n=18) |
|---|---|---|
| mean turns | **26.0** | **138.6** |
| max turns | 56 | 322 |
| harness cap | 900 s | 2400 s |
| hit the cap | **4/36 = 11%** | **9/18 = 50%** |

Confounds, all uncontrolled:

- **Scope.** The 2026-09-02 agent ran full simulations; SIGA's task prompts
  mention `geosx` **zero** times (Q3).
- **Machine load.** 119.98/128, from other users (Q1).
- **Adapter weight.** Three extra blocking checks that the SIGA arm never had.

**One correction to the recollection:** the SIGA arms were not timeout-free. The
900 s cap was a real ceiling — **4 of 36 rollouts sit at exactly 900 s and were
not flagged as errors**, so the honest historical truncation rate is **11%**, not
0%. Still far below 50%, but the old number was flattering.

**Sample size is not the explanation.** n=18 is small, but a 26 → 139 shift in
mean turns is far outside what 18 draws would produce.

**Also relevant:** `stealth/ox-alpha` *was* `glm-5.3-flash` under a stealth slug.
So any ox-alpha-vs-glm gap is within-model variance, not a model difference, and
the 51 ox-alpha rollouts in the corpus are reusable as glm-5.3-flash data.

## Q3. Why are we running full simulations, unlike SIGA? Who decided that?

**Nobody decided it. It is emergent agent behaviour, and it is not in any plan.**

- The task prompt says *"Create an XML configuration for a solid mechanics
  simulation…"* — it never asks for the deck to be executed.
- The seed adapter (`PRIMER.md`, `memory/cheatsheet.md`) contains no instruction
  to run `geosx`.
- No planning document requests it.

The agent decided to verify end to end on its own, and wrote itself a memory file
recording the consequences:

> *"a 4680-element elastoplastic wellbore run took ~5 min/step instead of ~35 s"*
> … *"cost me a 40-minute run"*
> — `.claude_home/.claude/projects/-workspace/memory/geos-run-environment.md`

At 12:24 PT there were **9 concurrent `geosx` processes** at 1000–1800% CPU each,
several running 8–14 minutes (`PoroElastic_Mandel`,
`PoroElastic_Mandel_benchmark_fim`, `triaxialDriver`).

**DECISION (Matt, 2026-09-02): use GEOS for lint checking and validation only —
never a solve.**

Rationale: the deck is scored on structure against a reference deck. A converged
simulation contributes nothing to the score and costs the entire wall-clock
budget. **Keep both check paths** — `xmllint` for XML well-formedness and
`geosx --validate-input` for schema/semantic validity — because, as established
during the rebuttal process, **the two are subtly different** and each catches
things the other does not.

Implemented as an explicit negative constraint in the adapter/task instructions.

## Q4. Is the harness vanilla Claude Code, with the same GEOS access as SIGA?

**Harness: near-vanilla, and the same configuration SIGA's CC arm used.** Claude
Code with `--disallowedTools Skill, AskUserQuestion, Task, Agent, TaskCreate` and
`--strict-mcp-config`, mounting geos-rag (`search_navigator`, `search_schema`,

## Q5. What does decision-making look like — vanilla CC vs + the SIGA adapter?

Measured tool-call mix. **The profile is dominated by shell work in both, and
varies enormously by model.**

| arm | calls/rollout | shell | file ops | RAG search |
|---|---|---|---|---|
| SIGA `geos_eval20_baseline` | 25.0 | 56.2% | 31.4% | 10.1% |
| SIGA `geos_eval20_gptoss_baseline` | 14.1 | 0% | 33.5% | **43.0%** |
| 2026-09-02, CC+adapter+glm | **~139** | **66.5%** | 20.6% | 8.3% |

Two things worth noting:

1. **The RAG tools — the adapter's main retrieval affordance — are used ~8–10%
   of the time** by shell-heavy models, and the agent prefers `Bash` (grep, find,
   cat over `/geos_lib`) to the curated search tools. This is the same shape as
   the local `memory_lookup` result (called **zero** times while verified
   functional) and as arXiv:2608.14036, which finds skills act as procedural
   anchors (65.7%) far more than knowledge injection (4.5%).
2. **`gptoss` inverts the profile entirely** — 43% RAG, no shell. So "what the
   adapter does to decision-making" is not model-independent, which is a direct
   argument for the cross-model panel.

## Q6. Bitter lesson: should we evolve from scratch rather than from a handcrafted prior?

Matt's framing: if we were more bitter-lesson-pilled, wouldn't we drop the SIGA
adapter as a starting point?

**Position: the SIGA adapter is a reasonable seed, and the bitter-lesson worry is
better answered by an experiment than by an argument — so run both.** See
[`EXPERIMENT_PLAN.md`](EXPERIMENT_PLAN.md) §5, arm **E0-scratch**.

Reasons the handcrafted seed is defensible *here specifically*:

- **The bitter lesson is about compute-scaled learning beating handcrafted
  priors. We have no training compute** (`PROJECT_PRIMER.md` §3.1), so the
  scaling limit the lesson describes is not reachable. In a sample-starved
  text-space search, a good seed is not a prior competing with scale — it is the
  only thing that makes ~17 tasks × 2–3 seeds informative at all.
- **RLMOpt (2608.10471) reports that gains are set by seed headroom, not search
  budget.** That cuts both ways and is the strongest reason to actually test it:
  a strong seed may leave nothing to find, which is exactly the pre-registered
  null.
- **A from-scratch seed is not neutral either.** An empty adapter is itself a
  choice, and the honest comparison needs both endpoints.

Reasons to run the scratch arm anyway:

- It converts "is our prior load-bearing or limiting?" from a debate into a
  paired measurement, and it is the cleanest test of whether the loop can
  *discover* what SIGA's authors hand-derived.
- If from-scratch converges toward the handcrafted adapter, that is a strong
  positive result about the loop. If it plateaus below, the prior is earning its
  place. If it overtakes, the prior is a ceiling — the most interesting outcome
  and the one we would otherwise never see.
- **Cost is the objection**, not principle: from-scratch needs more rounds
  precisely because it starts with less. Budget it explicitly rather than
  smuggling it in.
